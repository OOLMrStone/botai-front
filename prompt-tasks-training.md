## Goal

Заменить заглушку `/tasks` законченным вертикальным срезом:

`каталог -> тема -> настройка пакета -> решение -> проверка -> разбор -> избранное -> продолжение`

Добавить отдельную вкладку-заглушку `Пробники`. Реализовать 6 самостоятельных моковых задач номера 1, чтобы проверить текст, KaTeX, изображения и три сложности.

## Requirements

Реализуй все требования из `IMPLEMENTATION-SPEC-TASKS.md`, включая:

- каталог частей 1/2 и избранного
- grid номеров с inline-раскрытием на две колонки
- темы, прогресс и шторку настройки
- status scrubber с short tap и точным hold-drag режимом
- одну задачу на экран в общей стабильной оболочке
- автосохранение черновиков и resume
- отдельный экран перед общей проверкой
- клиентскую проверку по ответам, пришедшим в JSON
- решения, validated states и редактирование ответа
- рабочие закладки и полный flow избранного
- disabled placeholders карандаша и двух ластиков
- responsive/keyboard/safe-area поведение
- skeleton/error/empty/disabled states

Правильные ответы и решения намеренно приходят вместе с задачами. Не переносить проверку на сервер и не проектировать защиту ответов от просмотра в Network.

## Implementation spec

Следуй слоям и существующим аналогам проекта. Не складывай фичу в один компонент.

- Pages - композиция
- Config - данные, тексты, порядок, размеры, gesture constants
- Hooks - интерактивное поведение
- Stores - session/UI state
- Lib - чистая логика
- `lib/api` - единственная граница данных, даже когда внутри мок
- Components - view

Новая задача, тема или номер должны добавляться данными, без изменения renderer и selection logic. Один факт хранится в одном месте. Не создавай неиспользуемые абстракции и не копируй существующие visual states.

Особенно важно:

- переиспользовать существующий validated-field паттерн для рамок ответа
- маршруты добавить в единый route map
- тексты вынести в COPY/config
- размеры и responsive tokens добавить в `src/config/layout.ts`
- не хардкодить layout utilities в feature-компонентах в обход responsive skill
- сохранить текущие пользовательские изменения в dirty worktree

### KaTeX

Пользователь в текущем обсуждении явно одобрил KaTeX. Перед установкой соблюдай dependency-safety skill: выбери точную стабильную версию, не используй `latest`, выполни marker scan. Если установка требует отдельного системного разрешения или обнаружен подозрительный lifecycle script, остановись и запроси это явно.

## Out of scope - do not touch

- реальный backend
- импорт/парсинг РешуЕГЭ, ФИПИ, Яндекса или школ
- массовое наполнение банка
- рабочий canvas для карандаша и ластиков
- функциональность пробников
- финальная цветовая айдентика
- AI-помощник
- платежи
- несвязанные рефакторинги

## Acceptance criteria

Definition of done из `AGENTS.md` и полный раздел Acceptance criteria из `IMPLEMENTATION-SPEC-TASKS.md` обязательны.

Минимум:

1. `npm run lint` проходит чисто
2. Production-like build проходит
3. Все новые UI-состояния проверены в live preview, а не только по коду
4. Проверены 375x812, низкий экран, широкий/foldable viewport и desktop glance
5. Проверены клавиатура, safe area, отсутствие horizontal overflow и console errors
6. Проверены каталог, раскрытие, шторка, навигация, scrubber gesture, проверка, изменение ответа, решение, избранное, выход и resume
7. `SCOPE.md` обновлён
8. Итоговый отчёт кратко перечисляет файлы/архитектуру, проверки и известные ограничения; приложены screenshots

## Working style

- Сначала исследуй существующие аналоги, затем составь короткий план и реализуй
- Если работу можно безопасно разделить, используй агентов по требованию `AGENTS.md`, но не допускай параллельного редактирования одних файлов
- Не спрашивай о продуктовых решениях, уже зафиксированных в spec
- Не прерывай работу ради необязательных уточнений: выбирай самый простой вариант, согласованный с AGENTS.md, skills и существующими паттернами
- Останавливайся только при реальном блокере: отсутствующее разрешение, опасная dependency-ситуация или решение, которое невозможно вывести из spec/кода
- Работай до полностью проверенного результата, а не до первого компилирующегося варианта
