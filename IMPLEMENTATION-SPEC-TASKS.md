# Implementation spec: каталог и тренировки задач ЕГЭ

## 1. Цель первой реализации

Заменить заглушку `/tasks` полноценным мобильным сценарием тренировки:

`каталог номеров -> выбор темы -> настройка пакета -> решение -> экран перед проверкой -> проверка -> разбор -> избранное/продолжение`

Первая версия остаётся чёрно-белой и использует существующий визуальный язык BotAI. Она должна быть законченной по поведению, но работать на небольшом наборе моковых данных.

Тестовое наполнение: 24 самостоятельно написанные задачи номера 1 и 18 задач номера 2, поровну простых, средних и сложных. Набор обязан проверить text, KaTeX, image и длинный status scrubber.

## 2. Навигация и маршруты

### Нижняя навигация

Порядок вкладок:

1. `Главная`
2. `Задачи`
3. `Пробники`
4. `Профиль`

`Пробники` - отдельный маршрут и отдельная вкладка-заглушка. Функциональность пробников вне этой реализации. Это будущий самостоятельный продуктовый раздел со своими завершёнными попытками и статистикой, а не режим внутри задач.

### Маршруты

- `/tasks` - каталог задач
- новый route через единый route map для активной тренировки
- новый route `/mock-exams` или эквивалентное имя через route map для заглушки пробников

Точные slug и имена модулей агент выбирает по существующим аналогам. Строки маршрутов в компонентах запрещены.

### Возврат и продолжение

- Выход из активной тренировки выполняется стандартным крестиком в верхней панели
- Нажатие сразу сохраняет тренировку и возвращает в каталог задач без подтверждения
- На главной существующая карточка продолжения должна вести в сохранённую незавершённую тренировку
- При возврате из тренировки каталог сохраняет раскрытый номер и позицию прокрутки

## 3. Экран каталога `/tasks`

### Верх экрана

- Заголовок `Задачи` через существующий `ScreenHeading`
- Под заголовком спокойный переключатель из трёх пунктов:
  - `Часть 1`
  - `Часть 2`
  - `Избранное`
- Выбранный пункт запоминается при уходе и возвращении
- Переключение части закрывает раскрытую карточку номера

### Сетка номеров

- Две компактные карточки в строке
- Часть 1 показывает номера 1-12
- Часть 2 показывает номера 13-19
- Все номера присутствуют в конфиге с первого дня
- Номера без задач приглушены, содержат подпись `Скоро` и не раскрываются

Маленькая активная карточка содержит:

- номер ЕГЭ
- название номера
- стрелку раскрытия
- снизу тонкий progress track: светло-серый фон и чёрное заполнение
- при 100% дополнительно маленькую галочку

На маленькой карточке процент показан рядом с progress track.

### Раскрытие номера

- Тап работает по всей карточке
- Одновременно открыт только один номер
- Повторный тап сворачивает его
- Тап по другому номеру сворачивает прежний и раскрывает новый
- Страница не выполняет принудительную автопрокрутку
- Карточка остаётся на своей позиции, растягивается на обе колонки, а последующие grid-элементы сдвигаются вниз
- Соседняя карточка переносится в следующую свободную ячейку
- Высота раскрытого блока естественная: зависит от числа тем и не имеет искусственного фиксированного размера
- Перестроение должно выглядеть плавно; соблюдать правило проекта о compositor-only motion. Использовать существующий подход или FLIP/View Transition с безопасным fallback без новой animation-зависимости

В раскрытом блоке:

1. В шапке явно показан общий процент номера
2. Первая выделенная строка - `Все задачи`
3. Далее темы идут простым вертикальным списком
4. Каждая тема содержит название, процент без слова `решено` и progress track
5. Тап по `Все задачи` или теме открывает шторку настройки пакета

Источники, сборники и авторство в пользовательской классификации MVP не показывать.

## 4. Шторка настройки пакета

Небольшая нижняя шторка открывается поверх каталога и уже преднастроена. Основной сценарий - открыть и сразу нажать `Начать`.

### Количество

- Варианты: `5`, `10`, `20`, `Все`
- По умолчанию: `10`
- `Все` означает все ещё не решённые подходящие задачи
- Если доступных задач меньше выбранного количества, запускаются все доступные; соседние темы не подмешиваются

### Сложность

- Варианты: `Простые`, `Средние`, `Сложные`
- Можно выбрать несколько вариантов одновременно
- По умолчанию выбраны `Средние`
- Вариант с нулём доступных задач серый и неактивный
- В пакете задачи упорядочиваются от простых к сложным
- Точное соотношение сложностей внутри ограниченного пакета пока не оптимизировать: вынести стратегию выбора в чистую функцию, чтобы позднее изменить её без UI-правок

### Приоритет задач

1. Нерешённые
2. Ранее решённые неверно
3. Ранее решённые верно

Решённую задачу не показывать снова, пока остаются новые подходящие задачи. Это глобально определяется по `task.id`: если одна задача размечена несколькими темами, её статус общий во всех пакетах.

### Остальное

- Вверху динамическая строка с количеством и временем
- Время в MVP везде равно `0 мин`; расчёт будет добавлен позже
- Основная кнопка: `Начать`
- После завершённого пакета продолжение открывает ту же шторку с предыдущими настройками

## 5. Модель активной тренировки

Прежняя идея длинной ленты карточек отменена. На экране одновременно показывается одна задача.

Экран состоит из общей неподвижной оболочки:

1. Верхняя панель с иконкой выхода и сегментным навигатором
2. Отдельная прокручиваемая область карточки текущей задачи
3. Нижняя общая панель: назад, вперёд/к проверке, поле ответа

При переключении меняется только содержимое задачи и значение её ответа. Общие элементы оболочки не размонтируются.

### Состояния задачи

Логический статус проверки:

- `unverified`
- `correct`
- `incorrect`

Отдельно хранится наличие чернового ответа. Визуальные состояния сегмента:

- без ответа - дефолтный/белый
- ответ сохранён, но не проверен - серый
- верно - зелёный
- неверно - красный

Текущая задача обозначена маленьким указателем под сегментом.

### Автосохранение

- Ответ автоматически сохраняется при переходе на другую задачу
- Черновики и статусы сессии переживают выход
- При редактировании ранее проверенного ответа поле и сегмент немедленно возвращаются в `unverified`
- Правильный ответ редактируется в том же поле; отдельной формы нет

## 6. Сегментный навигатор задач

Это не обычный progress bar, а компактный status scrubber.

### Обычное состояние

- Один сегмент на одну задачу
- Цвет сегмента показывает состояние
- Короткий тап по сегменту сразу открывает приблизительно выбранную задачу
- Навигатор поддерживает 5, 10, 20 и большое количество задач

### Точный режим удержанием

- Press-and-hold в области навигатора включает увеличенный режим
- В месте взаимодействия сегменты раздвигаются и получают аккуратные номера
- Увеличенная шкала раскрывается только внутри заранее зарезервированной собственной области и не перекрывает карточку задачи
- Пока палец удерживается, горизонтальное движение выбирает номер
- Движение увеличенной шкалы намеренно медленнее движения пальца, чтобы точно остановиться на задаче
- Вертикальное отклонение пальца не отменяет жест и не меняет выбор
- Использовать pointer capture; на отпускании открыть выбранную задачу и свернуть увеличенный режим
- Указатель снизу следует за выбираемой задачей
- Коэффициент замедления, порог удержания и размеры живут в конфиге
- Учесть `prefers-reduced-motion` и touch/pointer устройства

### Экран перед проверкой

После последней задачи есть дополнительная логическая позиция справа от сегментов. На ней указатель смещается вправо и визуально поворачивается в сторону экрана проверки.

- На первой задаче кнопка назад серая и неактивная
- На последней задаче стрелка вперёд исчезает
- Вместо неё появляется более широкая горизонтальная кнопка `К проверке`
- Из-за её ширины область ответа на последней задаче становится уже
- После проверки навигация работает так же; экран проверки остаётся доступен

## 7. Карточка задачи

Карточка белая на нейтральном чёрно-белом фоне. Она строится полностью из JSON и не знает конкретного типа задания.

### Содержимое

- Заголовок `Задание N`, где N - позиция внутри текущего пакета
- Экзаменационный номер и тема внутри карточки не показываются
- Условие из последовательности блоков:
  - `text`
  - `latex`
  - `image`
- Решение использует тот же block renderer
- При длинном условии прокручивается только область карточки; верхняя и нижняя панели остаются на месте

### Действия справа сверху

- Рабочая закладка избранного
- Иконка сложной задачи для `hard` (пока условная иконка гроба)
- Серые отключённые иконки будущих инструментов:
  - карандаш
  - пиксельный/частичный ластик
  - объектный ластик, удаляющий целый штрих

Не делать функциональность рисования в MVP. Будущее назначение - рисование прямо поверх чертежей.

### Ответ

- Поле находится в общей нижней панели, но хранит значение конкретной задачи
- `inputMode` вызывает системную числовую клавиатуру
- Принимаются точка и запятая; отдельная кнопка минуса не нужна
- Шрифт поля не меньше 16px, чтобы Safari не увеличивал страницу
- При открытой клавиатуре активное поле плавно прокручивается/позиционируется над `VisualViewport`; не откреплять его в отдельный визуальный компонент
- Нижняя панель соблюдает safe area

Состояния поля повторяют уже существующий паттерн регистрационных полей:

- непроверено - обычная рамка
- верно - зелёная рамка и галочка
- неверно - красная рамка без изобретения нового паттерна
- при вводе в красное или зелёное поле оно сразу возвращается в обычное состояние

Нужно переиспользовать существующие primitive/стили `ValidatedField` или извлечь общий state styling и мигрировать потребителей; не копировать второй вариант.

### Решение

- После проверки у каждой проверенной задачи появляется `Посмотреть решение`
- Решение не раскрывается автоматически
- Кнопка раскрывает решение внутри карточки под условием

## 8. Экран перед проверкой и проверка

Экран проверки использует ту же общую оболочку вместо карточки задачи.

До проверки он показывает:

- сколько ответов заполнено
- сколько не заполнено
- короткое напоминание всё проверить
- пропущенные номера крупными строками по одному в ряд; каждая строка явно возвращает к заданию
- если всё заполнено: `Все ответы заполнены`
- тап по номеру возвращает прямо к соответствующей задаче

Внизу находится основная кнопка `Проверить`. Отдельного confirm dialog нет: этот экран сам является осознанным подтверждением. Проверять разрешено и с пустыми ответами.

### Клиентская проверка

- Правильный ответ и решение приходят в том же JSON, что и задача
- UI не показывает их до проверки, но криптографически/сетевым способом они не скрываются
- Проверка выполняется на фронтенде
- Нормализация минимум: trim, русская запятая -> точка, числовое эквивалентное представление
- За один запуск проверяются только задачи в `unverified`
- После проверки пользователь автоматически попадает на задачу 1
- Результаты видны в сегментах и состояниях полей

После редактирования хотя бы одного ответа `Проверить` снова активна. Если нет непроверенных ответов, она визуально ослаблена/неактивна.

На экране проверки под ней находится `Продолжить тренировку`:

- пока остаются ошибки, это вторичное действие
- когда все задачи решены верно, `Проверить` ослабевает, а `Продолжить тренировку` становится основным действием
- продолжение открывает шторку с последними настройками

## 9. Избранное

### Вкладка каталога

`Избранное` - третий пункт верхнего переключателя `/tasks`.

Содержимое - grid из тех же компактных карточек:

1. Первая карточка `Все избранные`
2. Затем конкретные сохранённые задачи, новые сверху

Карточка конкретной задачи показывает только экзаменационный номер и короткий `#ID`, без темы и прогресса. Тап открывает тренировочную оболочку с одной задачей.

### Все избранные

- Если сохранено 5 задач или меньше, пакет запускается сразу
- Если больше 5, сначала открывается обычная шторка настройки
- Тренировка работает как snapshot: снятие закладки не удаляет задачу из уже запущенного пакета
- При полном выходе из одиночной или общей тренировки избранного задаётся вопрос `Убрать решённые задачи из избранного?`
- Кнопки: `Убрать` / `Оставить`
- `Убрать` удаляет только задачи, решённые верно в текущей тренировке
- Неверные и пропущенные остаются
- Снятая вручную закладка применяется после выхода, но текущий экран не закрывается

Пустое состояние: `Сохраняй сложные задачи, чтобы вернуться к ним позже`.

## 10. Данные и JSON

Точные TypeScript-имена агент согласует со стилем проекта, но контракт обязан выражать следующую модель:

```ts
type Difficulty = 'easy' | 'medium' | 'hard';

type TaskBlock =
  | { type: 'text'; value: string }
  | { type: 'latex'; value: string }
  | { type: 'image'; src: string; alt: string; aspectRatio?: number };

interface TrainingTask {
  id: string;
  examPart: 1 | 2;
  examNumber: number;
  topicIds: string[];
  difficulty: Difficulty;
  content: TaskBlock[];
  acceptedAnswers: string[];
  solution: TaskBlock[];
  provenance: {
    kind: 'original' | 'licensed' | 'official';
    author?: string;
    sourceUrl?: string;
  };
}
```

Дополнительные модели:

- конфиг частей, номеров и тем
- training session со snapshot `taskIds`
- draft answer по `taskId`
- status по `taskId`
- избранное по `taskId`
- общая история решения по `taskId`, независимо от темы/пакета
- сохранённые настройки последней шторки

Все данные приходят через `src/lib/api/*`. В моковом режиме API может возвращать локальные конфиги, но компоненты не импортируют банк задач напрямую. Правильные ответы присутствуют в DTO задачи по явному продуктовому решению.

## 12. Архитектурная декомпозиция

Обязательное направление зависимостей:

- `config/` - каталог, темы, моковые задачи, copy, timings, gesture/layout constants
- `lib/` - чистая сборка пакета, нормализация ответа, вычисление прогресса и статусов
- `lib/api/` - загрузка задач/сессии и сохранение прогресса/избранного
- `stores/` - UI/session state без fetch-логики
- `hooks/` - поведение каталога, тренировки, scrubber, VisualViewport
- `components/tasks/` - view-компоненты
- `app/` - только композиция

Предпочтительная декомпозиция ролей, с корректировкой под аналоги проекта:

- `TaskCatalog`
- `ExamPartTabs`
- `ExamNumberGrid`
- `ExamNumberCard`
- `ExpandedNumberCard`
- `TrainingSetupSheet`
- `TrainingShell`
- `TaskStatusScrubber`
- `TaskCard`
- `TaskBlockRenderer`
- `TrainingControls`
- `TrainingReview`
- `FavoritesGrid`

Поведение вынести минимум в:

- чистый package selector
- чистый answer normalizer/checker
- session store
- scrubber interaction hook
- keyboard/VisualViewport hook

Это ориентир по ролям, а не требование создать пустые абстракции. Не делать файл/хук, если он не используется. Компонент около 100 строк или со сложным условным JSX разделять по ответственности.

## 13. Responsive и motion

Обязателен `.claude/skills/responsive-ui/SKILL.md`.

- Каталог - scroll screen
- Тренировка - `h-svh` shell с фиксированными общими зонами и внутренним scroll только карточки
- Все размеры, gaps, touch targets, reserved scrubber area и safe-area offsets - из `src/config/layout.ts`
- Никаких `100vh`, `100vw`, `w-screen`, `h-screen`
- Touch targets не меньше проектного минимума
- Проверить узкие, высокие, низкие и широкие/foldable viewport
- Не растягивать mobile UI на планшете/desktop без ограничения читаемой ширины
- Layout обязан переживать 5, 10, 20 и большое число сегментов
- Анимации только transform/opacity
- Клавиатура не перекрывает поле и controls
- Reduced motion показывает корректный конечный state

## 14. Состояния и ошибки

Обязательны:

- loading skeleton для каталога и сессии
- единый `ErrorNote` + retry для запросов
- пустые состояния тем/избранного
- disabled состояния недоступных номеров, сложностей и навигационных стрелок
- восстановление повреждённой/устаревшей сохранённой сессии с безопасным возвратом в каталог
- отсутствие горизонтального overflow
- bookmark optimistic UI с восстановлением при ошибке сохранения

## 15. Scope

### В scope

- каталог 1-19
- раскрытие номера и темы
- настройка пакета
- 24 моковые авторские задачи номера 1 и 18 задач номера 2, чтобы проверять длинный scrubber
- формулы KaTeX и изображения
- training shell и scrubber
- клиентская проверка
- решения
- избранное
- resume с главной
- заглушка пробников
- документация и visual QA

### Вне scope

- реальный Spring-бэкенд
- массовый банк задач и импорт со сторонних сайтов
- функциональное рисование карандашом/ластиками
- полноценные пробники и их статистика
- финальный цветовой design code
- AI-подсказки
- сложный алгоритм пропорций difficulty
- реальный расчёт времени

## 16. Acceptance criteria

1. `/tasks` больше не заглушка; все три верхних режима и номера 1-19 отображаются корректно
2. Активный номер плавно раскрывается на две колонки; открыт максимум один
3. Шторка запускает пакет с согласованными defaults и disabled states
4. Тренировка поддерживает переходы, автосохранение, exit/resume и все четыре цвета сегментов
5. Short tap и точный hold-drag scrubber проверены пальцем/эмуляцией touch
6. Проверка выполняется на фронтенде по ответам из JSON и проверяет только `unverified`
7. Решение скрыто до проверки и раскрывается по запросу
8. Избранное работает, включая snapshot и очистку верно решённых при выходе
9. Клавиатура не перекрывает поле на iOS-подобном viewport
10. Существующие экраны не сломаны, визуальный язык и validated states переиспользованы
11. `npm run lint` и релевантная production-like сборка проходят
12. `SCOPE.md` обновлён и не противоречит реализации
13. UI проверен по `verify-ui` минимум на 375x812, низком viewport, широком/foldable viewport и desktop glance; console/network чистые
14. В итоговом отчёте приложены screenshots и перечислены проверенные интеракции
